## The problem

x402 lets an API ask for payment with HTTP status 402 and get paid in USDC within the same request. That works for agents and phones only if the signing key is safe. Most Android crypto wallets protect the seed by encrypting it with a hardware-backed key. I wanted to build that pattern from scratch and measure what it actually protects.

## What I built

Four steps, each runnable on its own:

1. A Node client using the official x402 library.
2. A Kotlin CLI that builds the EIP-712 signature by hand.
3. An Android app with a hardcoded key, to get the flow working.
4. The real thing: a StrongBox (Titan M2) AES-256-GCM key, gated by biometrics and non-extractable, that unwraps the seed only to sign. A later step adds payment history that records the security level used for every signature.

```text
StrongBox wrap key (biometric)
   ──unwrap──► seed in app memory
   ──► EIP-712 TransferWithAuthorization (EIP-3009)
   ──► X-PAYMENT header
   ──► USDC settles on Base Sepolia
```

## The trade-off I documented

StrongBox can't sign with secp256k1, the curve Ethereum uses, so the seed has to pass through app memory to sign. My own analysis found that this exposure is not brief: the crypto library leaves copies of the key on the heap, where a heap dump can recover them. That is the weakness of the pattern most wallets ship. Stating it plainly is more useful than a "keys never leave hardware" claim.

## The fix I'm working toward

- **Sign inside hardware:** a P-256 passkey signs inside StrongBox, and a smart-contract wallet verifies the signature on-chain.
- **Prove the device:** Android Key Attestation goes in the payment envelope, so a merchant can verify the request came from a real phone.
- **Tested so far:** on a separate branch, StrongBox rejected Ed25519, while a TEE-backed Ed25519 signer worked end-to-end on a Pixel 10 Pro. That work also surfaced a bug I fixed upstream in Multipaz.
