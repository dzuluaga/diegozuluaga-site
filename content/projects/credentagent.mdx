## The problem

AI agents can now call tools that move money or unlock things. The hard question is not "can the agent do it?" but "who said it could, and can we prove it?" An API key in the agent proves nothing about the person, and a pop-up "Approve?" button proves very little more.

CredentAgent makes the human step verifiable. Before an agent completes something consequential (a payment, an age-gated purchase, an access grant), it asks the user's phone wallet for a credential, and the wallet shares only the one fact that is needed. Identity leads; payments is one application.

## What I built

Two Apache-2.0 npm packages, extracted from my earlier [Digital Credential MCP Server](/projects/digital-credential-mcp-server):

- **Gate** (`@openmobilehub/credentagent-gate`). Call `mount(app)` on any Express host and it adds the ceremony routes. Merchants write a typed policy such as `age.over(21)`, `membership.discount(10)` or `payment.in("usd")`, with `required`/`optional` and `.when()` conditions, and the gate turns it into a serializable manifest the agent can read.
- **Storefront** (`@openmobilehub/credentagent-storefront`). `createStorefront()` returns a complete MCP shopping server with nine tools and an embedded widget, so a demo merchant is one call.

```text
Agent (Claude, ChatGPT, goose)
   │  tool call creates a proof link
   ▼
Gate ──► browser page ──► phone wallet
   ▲                          │  passkey, mdoc or SD-JWT
   └── poll: proof complete ◄─┘
       payment settles last (x402, Hedera testnet)
```

Every rail ends in one shared `completeOrder` path, and enforcement is server-side, so the agent can never skip a check.

## Decisions worth talking about

- **Honesty in the types.** The current trust level is `presence-only-demo`: there is no issuer trust anchor yet, so a self-crafted mdoc would pass. Rather than hide that, the status is encoded in the API and written down in the README and roadmap.
- **Six written security invariants** guard the flows, and work is spec-driven (specs 001 to 007).
- **Signed cart mandate, stateless orders.** The cart travels signed, so serverless instances don't need shared session state ("stateless cart transport, not a stateless server").
- **Who holds spending authority.** An open design memo argues the wallet, not the merchant server, should hold it for human-not-present flows.
